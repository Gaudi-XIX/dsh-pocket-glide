## 一、结论（先行）

**支持 Lead 的假设，并把它从「源码上说得通」升级为「可离线复现」。** 置信度：**高（源码逐行 + 宿主落盘 + 日志三方对齐 + 探针复现四重证据）**。

一句话机制：草稿态（还没有会话）点发送 → `send()` 里 `await ensureSession()` 先在宿主建了一个**零消息会话**，随后还要 `await applyDraftPending(...)` 把草稿里挂起的 preset/model/permission 逐条刷进这个新会话；**这段 await（实测 0.4～2.8 秒）期间用户点「返回主页」，`showSessionList()` 把全局 `activeSession` 清成 `null`**；`ensureSession()` 仍然返回真值 id 所以守卫放过，但下一行 `const owner=activeSession` 读到的是 `null` → 发出的 `session.prompt` 带 `sessionId:null` → 宿主网关严格校验拒收（`gateway/input-invalid`）→ 那条消息**从未进入宿主**，而刚建好的空会话已经落盘 → 用户再点进去就是一个**完全空的会话**。失败分支还会把原文回填输入框并弹一次错误，所以现象是「报过错 + 会话空」，不是纯静默（与 Lead m00411 第 6 点一致，已实证）。

**关键限定（比 Lead 的表述更严格）：竞态窗口只由 `applyDraftPending` 的真实 RPC 撑开。** 没有草稿待办时，`ensureSession()` 里从 `activeSession=created.sessionId` 到 `return` 之间只剩微任务，宏任务手势插不进来；探针 D 档实测：手势落在 `session.create` 的 await 里也**不会**出事。也就是说，触发还需要一个前置条件：**用户在草稿态动过「+」里的预设/模型/权限中至少一项**（或后续把 `ensureSession` 内部 await 拉长的任何改动）。

## 二、逐条回答（Lead 的 A～D 与 task-1 五问）

### A. 微任务顺序的反证 —— 成立，且已被探针证实

`await ensureSession()` 返回到 `const owner=activeSession` 是同一条微任务的连续体（`lib/pages.js:2179`，逐字为 `try{if(!activeSession&&!(await ensureSession()))throw new Error(L.sendFailed||'Send failed');const owner=activeSession;markRowRunning(owner);`），用户事件是宏任务，插不进这段。所以 `owner` 变 `null` 只能发生在 `ensureSession()` **内部**的 await 上。

代码里那个 await 就一处：`lib/pages.js:1720` 末段 `draftWorkspaceId=null;activeSession=created.sessionId;` → `lib/pages.js:1724` `followStream=true;await applyDraftPending(created.sessionId);history.replaceState(...);openRealtime(...);return created.sessionId`。**赋值在前、await 在后、return 读全局在最后** —— 这是缺陷本体。`lib/pages.js:1714` `applyDraftPending` 会串行发 `agentPreset.select` / `session.selectModel` / `command.execute('/permission …')` 最多三个真实 RPC；它开头 `if(!pending||!sessionId)return;` —— 无待办时是空过（仅微任务）。

D 档反证：无待办时手势打在 `session.create` 的 20ms await 里，`send()` 依然拿到真 id、prompt 成功。**没有反例。**

### B. 乐观绘制与「马上退出才触发」+ 消息不留痕 —— 成立

`send()` 在读 `owner` **之前**已经做了乐观渲染：`optimisticPrompts.push(optimistic);sessionBlank=false;armAwaitingTurn(afterSeq);agentRunning=true;promptEl.value='';paintMessages(messagesWithOptimistic(...))`（`lib/pages.js:2179`）。所以用户当下看到的是「消息已发出去」。

失败后走内层 catch（同一行内）：`if(activeSession===owner&&optimisticPrompts.includes(optimistic))` —— 此处 `owner` 与 `activeSession` **同为 `null`，条件为真**（Lead 提示的反直觉细节，探针 C/E 档实测到这一步），于是：撤乐观泡 → `clearAwaitingTurn()` → `agentRunning=false` → `showError('chatError',e)` → 原文回填 `promptEl` → 重绘 → `await refreshActiveSessionSummary()`。**乐观泡被过滤掉（`optimisticPrompts.filter(item=>item.id!==optimistic.id)`），宿主侧也从未收到这条消息 ⇒ 这条消息在两端都不留痕**，用户只剩输入框里回来的文本。慢一点退（等 flush 结束再退）就不触发 —— 与「马上退出才触发」一致。

补充一个副作用（探针 C/E 档目击，Lead 未提）：竞态后 `ensureSession()` 仍执行了 `history.replaceState({view:'chat',sessionId:created.sessionId})` 与 `openRealtime(created.sessionId)`，**把已经退回主页的视图路由又改回 chat 并开了一条 SSE**。这解释了现场日志里 `15:33:01.985Z doc url=/?revalidate=1` 前后用户为什么又进到了那个空会话里。
