## 一、结论先行

**用户说的「不能滑动」在代码层找不到队列坞专属的滑动拦截。** 四个候选里只有一条成立，且它不是「拦截触摸」：

| 判定 | 内容 |
| --- | --- |
| **(a) 真滑不动（touch 被拦 / scrollTop 被回写）** | **不成立**。队列相关函数里**没有任何一处 `scrollTop=` 写入**。全文件 `scrollTop=` 只有 8 处写入点（见 §三调用图），没有一处落在 `renderQueueDock` / `updateQueue` / `syncQueueHeight` / `syncComposerHeight` 的调用链上。`.messages` 上也没有 `touchmove` 的 `preventDefault`（`:2303` 全 `passive:true`）。 |
| **(b) 能滑但被弹回底部（跟随状态机劫持）** | **部分成立，但归因要改**：真正的橡皮筋来自**已有的跟随状态机**（`:2351` `programmaticScroll` 250ms 静默窗 + `:2431` `settleTailStick` ×4），**队列坞只是让这条链在排队期间必然被激活**（`:1836` `agent/inbox/spliced` → `:1316` `scheduleProjectionsSync` → `:1258` `updateQueue`，以及 `:1816` `flushStreamRender` 每帧把 `lastHistoryKey=''`）。这与「排队」无因果专属，是**排队期间流式还在跑**这一并存条件导致的。 |
| **队列坞引入的真实几何效应** | **成立，但方向与用户直觉相反**：`.composer` 是 `position:fixed`（`:548`），**`.messages` 的 `clientHeight` 不因队列坞出现而缩小**；变的是 `padding-bottom`（`:540` `--queue-h`），于是 **`scrollHeight` 增大而 `scrollTop` 不动**（`overflow-anchor:none`）。读者在底部时 `transcriptDistance` 由 0 跳到 ≈`--queue-h`（离线探针：2 行队列 = 131px，3 行 = 168px），**这会让 `isNearBottom` 立刻判否 → `followStream` 被主动关掉**（`:1522` 的 `'br'` 分支）——即队列坞的出现反而**解除了**橡皮筋，不是加重它。 |
| **反向效应（真正的「弹回」）** | **成立**：队列坞**消失**时（消息被消费 / 被 remove），`--queue-h` → `0px`（`:1331`），`scrollHeight` 骤减，浏览器把 `scrollTop` **夹到新底部**，`transcriptDistance` 归 0 → `isNearBottom=true` → `followStream` 被重新点亮。用户上滑时正好撞上这一下，观感就是「一滑就被弹回底部」。这是**布局回缩造成的被动回弹，不是代码写 `scrollTop`**。 |
| **嵌套滚动 / 手势抢走** | **成立但不足以致瘫**：`.queue-list{max-height:180px;overflow-y:auto}`（`:548`）确实在 `#composer` 内、`.composer` 有 `pointer-events:none` 但 `.queue-dock`/`.todo-dock` 有 `pointer-events:auto`。手指落在 dock 附近上滑时，若 dock 内条目总高 > 180px 会**被 dock 吃掉**；但这只影响 dock 那一小块区域（约屏幕下方 130–170px），不影响上方转录区。 |
| **可视区骤减 / 无可滚范围** | **不成立**：因 `.composer` 是 `position:fixed`，转录区可视高度**不减**。离线探针算得 dock 最高 158px 时，只要正文超过 ≈`viewport − 537px` 就有可滚范围。长会话必然有范围。 |

**一句话定性：这不是「滑不动」，是「排队期间滚动跟随被反复重新点亮 + 队列坞高度变化造成 scrollHeight 抖动」的观感问题。真机确认需要一步复现（见 §五）。**

**回答 Lead 的第 1 问**：按代码证据，**(b) 成立、(a) 不成立**——但要补一句更准确的话：不是「跟随把用户弹回底部」那么单一，而是**跟随状态机的静默窗**（`programmaticScroll` 每帧续期 250ms，`settleTailStick` 每 120ms 再续）在流式期间**让读者的滚动事件永远进不了重判分支**，同时队列坞的 `--queue-h` 来回变又把 `isNearBottom` 的输入搅乱。两者叠加才出现用户描述的现象。这属于「跟随链没修干净」，不是「队列坞拦了触摸」。

## 二、候选逐条判定表（含逐字片段）

### 候选 1：重绘贴底劫持 —— **部分成立（是激活源，不是队列坞本身）**

**队列坞刷回路径本身不碰滚动**（`:1258`）：

```js
function updateQueue(projections){queuedTurn=queuedRowsOf(projections);if(queueEditing!==null)return;renderQueueDock()}
```

`renderQueueDock`（`:1314`）只做三件事：`host.hidden` 切换、`document.body.classList.toggle('queue-open',visible)`、`host.innerHTML=...`，末句 `syncQueueHeight(host)`（`:1331`）只写一个 CSS 变量：

```js
function syncQueueHeight(host){document.body.style.setProperty('--queue-h',host.hidden?'0px':(host.offsetHeight+10)+'px')}
```

**但它被包在一条会整段重绘的链里**：

- `:1836` `applyStreamEventFrame` 末句：
  ```js
  if(type==='goal/change'||type==='agent/inbox/spliced'||type==='user/message'||type==='turn/start'||type==='turn/end')scheduleProjectionsSync(sessionId)
  ```
  ⇒ **排队动作本身产生的事件类型恰好是 `agent/inbox/spliced`**，队列坞刷回与流式帧是同一批。
- `:1316` `scheduleProjectionsSync`（250ms 去抖）→ `:1315` `fetchProjectionsNow` → `:1815` `applyHistory`。
- `applyHistory` 的 key **不含队列内容**（这是 Lead 给的关键点，已复核为真）：
  ```js
  const key=JSON.stringify([messages,pendingQuestion?.rpcId||null,agentRunning,currentTodos,todoExpanded]);
  ```
  ⇒ **纯队列变化不会**因 key 变化触发 `paintMessages`。**候选 1 中「`updateQueue` 直接触发 `paintMessages`」这一条不成立。**
- **真正的重绘来自另一头**（`:1816` `flushStreamRender`）：
  ```js
  if(streamNeedsFullPaint)paintMessages(messages,false);else patchLastStreamMessage(messages);streamNeedsFullPaint=false;lastHistoryKey='';idlePollMs=HISTORY_POLL_IDLE_MS
  ```
  `lastHistoryKey=''` **主动作废 key** ⇒ 下一次 `applyHistory` 必然整段重绘。而 `flushStreamRender` 是每个 rAF 跑的（`:1817` `queueStreamRender`），且非 chunk 事件都会置 `streamNeedsFullPaint`。**排队期间转录区每帧都在走 `patchLastStreamMessage`，这就是跟随链被持续激活的原因。**

**`applyHistory` 的 key 修复价值判断：不需要改。** 队列不在 key 里是对的（队列是 dock 的事，不该让转录整段重绘）。

### 候选 2：布局抖动 —— **成立（方向与直觉相反，两头都有害）**

- CSS（`:540`，逐字）：
  ```css
  .messages{flex:1;min-height:0;overflow-y:auto;overscroll-behavior:contain;overflow-anchor:none;display:flex;flex-direction:column;gap:0;padding:18px 4px}.chat-open .messages{padding-top:4px;padding-bottom:calc(var(--composer-h) + var(--todo-h) + var(--queue-h) + var(--tunnel-warn-h))}
  ```
  `overflow-anchor:none` ⇒ **`scrollHeight` 变化不会自动修正 `scrollTop`**（这是设计选择，避免流式时锚点乱跳）。
- **出现方向**：`--queue-h` 0 → ≈131–168px，`scrollHeight` 增大、`scrollTop` 不动 ⇒ `transcriptDistance` 0 → 131/168 ⇒ `isNearBottom` 判否（`:2335`）。
- **消失方向**：`--queue-h` → `0px`，`scrollHeight` 骤减 ⇒ **浏览器把 `scrollTop` 夹到底** ⇒ 距离归 0 ⇒ `isNearBottom=true` ⇒ 跟随重新点亮。**这是用户观感里的「弹回」。**
- **`isNearBottom` 会不会误判**：会，但方向是**过严而非过松**。`:2335` 逐字：
  ```js
  function isNearBottom(box){const dist=transcriptDistance(box);lastDistance=dist;lastScrollHeight=box.scrollHeight;const settled=settledTranscriptHeight();return dist<=Math.min(SCROLL_FOLLOW_PX,Math.round(settled/2))}
  ```
  与 `:2318` `function transcriptDistance(box){return box.scrollHeight-box.scrollTop-box.clientHeight}`。
  队列坞出现后 `dist=131`（2 行）已超 `min(120, settled/2)` 的绝大多数取值 ⇒ **队列坞一出现就误判为「读者已离开底部」**，于是 `:1522`：
  ```js
  const near=typeof isNearBottom==='function'?isNearBottom(box):true;if(!near&&typeof followStream!=='undefined'&&followStream){followStream=false;if(typeof readTranscriptAnchor==='function')transcriptAnchor=readTranscriptAnchor(box);if(typeof probeMark==='function')probeMark('br')}
  ```
  把跟随关掉。**结论：队列坞的出现不是橡皮筋的成因，反而是它的解除阀；真正的橡皮筋在 dock 消失那一瞬。**
- **`settledTranscriptHeight()` 的取值**（`:2333`）：
  ```js
  function settledTranscriptHeight(){const box=$('messages');return box&&box.scrollHeight?box.scrollHeight:lastScrollHeight}
  ```
  它返回**当前** `scrollHeight`（非上一帧稳态值），因此 `Math.round(settled/2)` 会**跟着 `--queue-h` 一起变大**——长转录里 `settled/2 ≫ 120`，实际门槛恒为 120px，于是 131px 的队列偏移必然越界。**这一条是真正的误判放大器。**

### 候选 3：嵌套滚动区 —— **成立但范围有限**

- `.queue-list`（`:548`，逐字）：`.queue-list{display:grid;gap:6px;max-height:180px;overflow-y:auto;padding:7px 12px 9px}` —— **无 `overscroll-behavior`、无 `-webkit-overflow-scrolling:touch`、无 `touch-action`**。
- `.queue-dock`（`:548`）：`.queue-dock{flex:none;margin:0 0 8px;...;overflow:hidden;pointer-events:auto}` —— `overflow:hidden` + `pointer-events:auto`，且 `.composer` 本体是 `pointer-events:none`（`.composer{...pointer-events:none}`）。
- ⇒ **手指落在 dock 附近（屏幕底部 130–180px 带）上滑时，若队列条目超过 3 条，`.queue-list` 会先吃掉手势**；且 `.queue-list` 无 `overscroll-behavior`，滚动到底会把 overscroll 传给链上的 `.composer`，而 `.messages` 有 `overscroll-behavior:contain`（`:540`）但两者不是祖先-后代链（dock 在 composer 里，不在 messages 里），**所以 contain 不会截断 dock 的手势**——dock 内的滚动与转录区**互不接力**。
- 影响面：仅 dock 那一块。**不构成「整个页面滑不动」。**

### 候选 4：队列坞吃掉可视区 —— **不成立**

- `.composer` 是 `position:fixed`（`:548`），**脱离文档流**⇒ `.messages`（`flex:1;min-height:0`）的 `clientHeight` **不因 composer 变高而缩小**。离线探针实测推演（`geom-probe.mjs`，viewport 600）：`clientHeightBefore=600`、`clientHeightAfter=600`，恒定。
- 「`scrollHeight <= clientHeight` 根本没有可滚范围」：只有在正文本身短于 `viewport − composer-h(89) − queue-h(168)` ≈ 343px 时才发生，属极端边界，且此时用户也无内容可翻。

### 候选 5：其他机制

- **`document.body.classList.toggle('queue-open',visible)` 有无 CSS 消费者**：**无**。`:550` 有设计注释逐字写明：
  ```
  /* body class queue-open (renderQueueDock) has no CSS consumer by design: the queue dock reserves its height via --queue-h only (parent-card decision, do not re-litigate); todo-open below IS consumed by the .messages padding rules. */
  ```
  ⇒ 该 class **不可能**造成拦截。
- **`#composer .session-settings` 定位**（`:551`）：`#composer .session-settings{z-index:1;bottom:calc(76px + var(--todo-h) + var(--queue-h) + var(--tunnel-warn-h))}` —— 会随队列坞上移，**只影响面板自身，不影响转录区**。
- **`.scroll-anchors` 定位**（`:571`）：`bottom:calc(var(--composer-h)+var(--todo-h)+var(--queue-h)+var(--tunnel-warn-h)+16px)`，`pointer-events:none` ⇒ 不拦触摸。
- **`queueEditing` 期间的 textarea 聚焦**（`:1322` `startQueueEdit` 内 `if(box)box.focus()`）：聚焦会触发移动端键盘弹出 → `--kb` 变化 → `.composer` 的 `translateY(calc(-1*var(--kb,0px)))` 变化 → `.messages` 可视区变化 → `isNearBottom` 输入变化。**这是「编辑队列项时页面看起来跳了」的次要机制，与「不能滑动」不同源。**
- **`:1499` `ensureTranscriptFilled` 的门槛**（逐字）：
  ```js
  function ensureTranscriptFilled(){if(fillBusy||!activeSession)return;const box=$('messages');if(box.scrollHeight>box.clientHeight+8)return;if(!olderHasMore&&transcriptHasContent())return; ...
  ```
  **队列坞出现后 `scrollHeight` 变大 ⇒ 更容易满足首个 return ⇒ 队列坞不会触发自动补更早的页**。对「滑不动」无直接贡献（反而避免了自动补页带来的高度突增）。
- **`.messages` 缺 `-webkit-overflow-scrolling:touch`**：`:538`/`:592`/`:607`/`:617`/`:648`/`:659` 都有，`:540` 的 `.messages` **没有**。现代 iOS 已默认启用，**旧 iOS 上惯性滚动会明显变差，观感上「滑不动/很顿」**。这是一个**真实的、队列无关的**体验缺陷，值得单独修。

## 四、可复现的离线判据（探针）

探针：`F:\defws\tmp\20261019-queue-scroll\geom-probe.mjs`（纯算术，**不连桥、不开浏览器**）。
它把 `:2318` / `:2333` / `:2335` 三个函数**逐字照抄**，在建模的 `#messages` 几何上重放「队列坞出现」这一跳。

**判据（复制即跑）**：

```js
composerH = 58 + 16 + 10 + 5            // .composer-inner + host padding，syncComposerHeight 量到的值 ≈ 89px
queueDockH(n) = 8 + 19 + 7 + 9 + n*31 + (n-1)*6 + 8 + 2   // .queue-dock 实际盒高
queueVar(n) = queueDockH(n) + 10        // syncQueueHeight: offsetHeight + 10
// 出现后：scrollHeight += queueVar(n)；scrollTop 不变（overflow-anchor:none）
// → transcriptDistance 由 0 跳到 queueVar(n)
```

**跑出的实测数**（viewport 600）：

| 场景 | `--queue-h` | 出现后 `dist` | `isNearBottom` | 出现后剩余可滚范围 |
| --- | --- | --- | --- | --- |
| 正文 4000px + 2 行队列 | **131px** | **131** | **false** | 3624px |
| 正文 260px + 3 行队列 | **168px** | **168** | **false** | **−79px（无范围）** |
| 正文 420px + 3 行队列 | 168px | 168 | false | 81px |

**三条可判定的结论**：

1. **`clientHeight` 不变**（探针里 `clientHeightBefore === clientHeightAfter === 600`），坐实候选 4 不成立。
2. **`dist` 越界量恒 ≈ `--queue-h`**：2 行 = 131 > 门槛 120；3 行 = 168 ≫ 120。**只要队列坞一出现，`isNearBottom` 必判否、`followStream` 被 `:1522` 主动关掉。**
3. **「弹回」只发生在 dock 消失方向**：`--queue-h → 0` 时 `scrollHeight` 骤减 131/168px，`scrollTop` 被浏览器夹到底，`dist → 0` ⇒ `isNearBottom=true` ⇒ 跟随重新点亮。

**另有一条可判定的键盘判据**（纯代码，无需几何）：`send()` 在 `:2193` 读 `const readIntent=typeof followStream==='undefined'?true:followStream` 然后 `paintMessages(messagesWithOptimistic(currentTranscript(),true),readIntent)`。**用户点发送的那一刻，代码用「发送前的 followStream」决定要不要强制贴底**——排队时发送，用户本就贴在底部，属预期行为；但**若用户先上滑、再发一条排队消息**，这一行会按上滑前的状态走，属正常。可作为回归判据，不是缺陷。

## 八、Lead 复判与已落修复（2026-10-19）

### 8.1 推翻本报告「(a) 真滑不动不成立」的判定

本报告第一节把用户说的「滑不动」判为 **(a) 不成立、真身是 (b) 能滑但被弹回**。复判：**(a) 成立**，机制是 CSS 命中测试面（pointer-events）而不是手势拦截——本报告只查了 JS 侧（`touchstart/touchmove` 全 `passive:true`、`preventDefault` 不在触摸路径、`scrollTo/scrollBy` 0 处，这些 Lead 逐条复核为真），漏了 CSS 层。

机制（`lib/pages.js`，L548 的 CSS 巨行）：

- `#composer` 是 `position:fixed` 且 **`pointer-events:none`**，它同时是 `.todo-dock` / `.queue-dock` 的直接父元素；
- 两个 dock 自身 `pointer-events:auto`，且位置在 `.composer-inner` **之外**（`#composer` 内 DOM 顺序：`#sessionSettings` → `#todoDock` → `#queueDock` → … → `.composer-inner`）；
- 于是屏幕下方那条 **131–168px** 的带（`--queue-h` 实测 2 行队列＝131px，视觉上只是转录区的预留空白）落到的触摸被 dock 吃掉；
- 而这条带上**没有任何滚动语义**：`.queue-list` 限高 180px 且本例未溢出（无可滚范围）、dock 内文本/chip/边框/间距都不带点击处理（唯一交互是 `[data-queue-action]` 按钮、`.todo-header`、编辑 textarea）、`#composer` 不是 `#messages` 的祖先（无法链式滚动到正文）、再往上 `body{overflow:hidden}` 到头；
- ⇒ **既不滚坞、也不滚正文＝真·滑不动**，且它**只在有个头的排队坞/任务坞时出现**，与用户原话「有排队消息的时候，那个对话的页面好像还不能滑动」逐字吻合。

本报告候选 1/2 的「(b) 弹回」结论仍然成立且与 (a) **并存**：坞出现时 `--queue-h` 增大、`scrollHeight` 增而 `scrollTop` 不动（`overflow-anchor:none`）⇒ 距离越过 `SCROLL_FOLLOW_PX=120` ⇒ `:1522` 的 `'br'` 分支主动 `followStream=false`；坞消失时 `scrollHeight` 骤减、浏览器把 `scrollTop` 夹到底 ⇒ `isNearBottom` 重新为真 ⇒ 跟随重亮。两条是同一次布局变化的两个后果，用户感到的「不能滑」主要是 (a)。
