## 一、根因

提问卡（`#questionComposer`）在 `lib/pages.js` 的 `renderQuestionComposer()` 里只有**一条**出路：

- `.question-close`（×）→ `data-question-action="cancel"` → `cancelQuestionRequest()` → `rpc('interaction.cancel', …)`，即**真的取消这次提问**（agent 拿不到答案）。

同一函数里 `composer.hidden=true`：提问卡一出现，输入行被整块隐藏，卡片接管底部；而 CSS `.question-open .messages{padding-bottom:min(64vh,520px)}`（以及 `.chat-open.question-open .messages` 同值）又把转录区顶掉一大截。两者叠加的效果正是用户描述的：**卡片占着会话，想往下看会话却无路可走，界面上唯一的按钮是「取消」**。

用户要的不是取消，是「收起来看会话」——缺的是一个**非破坏性**的收起出口。

## 四、首版撞红既有 anti-fork 钉，已纠正（如实披露）

首版把收起后的净空写成 `calc(84px + env(safe-area-inset-bottom))`（84px = `.question-top` 13+10 padding + 44px 钮 + 1px 边框，加 `.question-composer` 的 10/5 padding 与安全区）。全量立刻出现新红：

```
test at test\pages-render-fixes.test.js:114:1
✖ T1 (r2-W2) the banner stack and the standalone base tier share one --todo-h formula
  AssertionError: the hardcoded composer band must stay swept from the sheet
```

该钉（`pages-render-fixes.test.js:127`）断言全表**不得**再出现 `calc(84px + env(safe-area-inset-bottom)`：这一写法正是历史上被清扫掉的「写死 composer 带」——输入框长到 150px 上限时它会失准。**把它换个用途（给提问卡用）一样是写死**，属真实回归，不是误报。

纠正：净空改为**页面自量**，与既有的 `--todo-h`/`--queue-h` 协议同源——`renderQuestionComposer()` 末尾把 `host.offsetHeight` 写进 `--question-h`，CSS 只消费 `var(--question-h,120px)`。同时把这一坑写进 `P-14` 的三条断言（`var(--question-h` 必须存在、`calc(84px + env…` 必须不存在、页面必须量），避免下次有人再写死。
