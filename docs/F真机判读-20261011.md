## 2. 这就是用户描述的那个东西

## 3. 三条先被排除，一条被确认

- **不是我的锚点复原**：整批 `rs` **0 次**。键盘收放全程 `restoreViewportAnchor` 没动过 `scrollTop`，
  所以「F 的一半是我自己引入的」这条自我怀疑**被数据否掉**。（注：这几轮人都贴底部，
  `scrollTop === maxScrollTop`，跟随态本来就会跳过复原，所以这既排除了嫌疑、也**还没测到**中间态。）
- **不是 visual viewport 平移**：`vv.offsetTop` 全程 **0**，Android 键盘顶起页面再还回那条路不成立。
- **不是顶边自动取页**：键盘收回段里行数/`scrollHeight` 没被前置页改变（1988 全程恒定）。
- **`resizes-content` 确实生效**：`vv.height === innerHeight === clientHeight` 三步一致 ⇒
  **我前面四支 CDP 夹具的前提没有被推翻**（这条最重要，它保住了之前所有模拟结论的地基）。

## 5. 埋点自身两个读数陷阱（下次改）

1. `rz` 同毫秒**成对**：`visualViewport.resize` 与 `window.resize` 都调 `scheduleViewport`，
   打点在共同下游 ⇒ 一次视口变化 = 两条 `rz`，别当成两次动作（本表已按此读）。
2. 没记「是不是人在滑」⇒ 手势引起的 `sc` 与浏览器自身补偿引起的 `sc` 只能靠「同毫秒紧邻 rz」
   这种间接方式区分。下一版加 `t`=touchstart 标记，直接判。

## 6. 修法为什么现在还不能定

末段那一跳**不是我们的 JS 造成的**（`rs=0`），是浏览器在 `resizes-content` 下对视口末段校正的
自带行为。要消掉它，就得改「键盘怎么占位」这一层，而那是个有代价的方向选择：

| 方案 | 效果 | 代价 |
|---|---|---|
| A. 视口去掉 `interactive-widget=resizes-content`（改回默认 resizes-visual / overlays） | 视口根本不再被键盘压缩 ⇒ 九步挤压和末段 56 px 一起消失 | 键盘会**盖住**输入框，输入区要靠 `visualViewport` 自己顶上去；当初选 resizes-content 就是为了别盖住 |
| B. 键盘动画期间不做任何贴底/补偿，等高度**稳定 150 ms** 后再一次性对齐 | 末段跳变被合并成一次、可预测 | 挤压过程会有轻微滞后 |
| C. 给滚动容器一个由稳定值驱动的 `min-height`，让末段那 56 px 校正不改变可滚范围 | 只治末段，不动动画过程 | 要处理与 composer 高度的耦合，风险中等 |

**我不按猜的改。** 这是方向决策（A 会改变输入区行为），要你拍；拍完我再实现，
并且改完**还要拿同一支埋点复测一次**——判据是「末段那 56 px 跳变消失、且 `rs` 仍为 0」。

## 7. 中段那种测到了：`rs` 13 次，而且是在和浏览器**来回抢写**（04:17 那批）

用户 12:17 补的描述是决定性的分叉：**贴着底是"弹一下"，停在会话中间是"屏幕闪一下"**。
新到的 1199 条读数里 `rz=575 / sc=611 / rs=13`，而 **13 次 `rs` 全部落在中段那几段**
（贴底那几轮一次都没有——`followStream` 本来就会早退，所以那不是巧合而是机制）。

典型一段（字段同前）：

```
sc  @108765 st=2102   ← 浏览器自己的 scroll anchoring 已经把位置校正好了
```

每 6–20 ms 一次，`st` 在 2086/2102/2145 之间来回摆。**「闪一下」就是这趟来回，不是单向位移。**
根因是 0.4.18 我加在 `scheduleViewport()` 里的那句 `restoreViewportAnchor()`：我当时判断
「视口变高浏览器钳了 scrollTop 且不发 scroll 事件，必须同一帧补回去」——**真机数据两条都错了**：
浏览器**会**发 scroll（`rz` 之后 1–2 ms 必有 `sc`），而且**它自己就锚得住**。我那一无疑是多余的一写，
多余的一写和浏览器的校正互相把对方当扰动，就成了抖动。

- 壳 267 352 → **267 150 B**（−202 B）。

## 8. 方向已拍并落地（用户 12:44 三条要求 → 0.4.22）

用户给的不是 A/B/C 选项，而是行为规格：**键盘弹出时页面不动、输入框在键盘上方；收回时到哪就是哪，
不闪不弹**。这等价于「不让布局视口被键盘压缩」＋「输入区自己抬」，即 §6 表里的 A 但避开它的代价
（键盘不再盖住输入框，因为输入框会抬）。

- 落地：`interactive-widget=resizes-visual` + `.composer`/`.scroll-anchors` 的 `translateY(calc(-1*var(--kb)))`
  ＋ `applyKeyboardLift()`（每拍 resize 重算，iOS 不叠）。**末段那 56 px 回弹的土壤被抽掉了**：
  布局视口既然不随键盘涨缩，就没有「钳制—回校正」这一步。
- 中段抖动（§7 那个 `rs` 抢写）已由 0.4.21 撤掉；两笔合起来才是 F 的完整答案——
  **它本来就是两个病**：中段=我抢写（已删），贴底=视口末段校正（已换声明）。
- 要求 1（进来不弹键盘）：代码里本来就没有进会话自动聚焦；唯一自动聚焦的是配对页 PIN 框，
  那是为省一次点击的有意设计，**等用户裁要不要也去掉**。
- **判据（重启后复测）**：`?probe=1` 打开，中段与贴底各开合键盘两三次 ⇒ 期望
  ① `rs = 0`（已经没有这条代码）；② `rz` 之后 `innerHeight/clientHeight` **不再变化**
  （视口不被压缩，也就没有 704→648 那一步）；③ 若 `vv.height` 变小而 `innerHeight` 不变，
  正是我们要的 resizes-visual 形态，此时 `--kb` 就是抬起量。


## 9. 埋点标记的持久化边界（12:5x 重启后实测，别再按「持久化」三个字理解它）

0.4.20 把 `?probe` 存进 localStorage（6 小时到期），当时想的是「页面自己会改写 URL，所以要看不住」。
**今天重启后发现它挡得住改写、挡不住换源**：

```
12:54:31  宿主重启（0.4.22 生效）
12:56:36  Tunnel online: https://mileage-taught-chrome-excel.trycloudflare.com   ← 换了随机名
12:57:45  device paired mode=tunnel
之后      kbprobe 新行 = 0
```

localStorage 按 **origin** 隔离，而快隧道的随机域名每次 cloudflared 重启都会变 ⇒ 新域名是新 origin，
旧 origin 里的 `pocketProbe` 根本读不到。**结论：这台机器的"埋点是否开着"只能靠
每次重启/换隧道后重新用带 `?probe=1` 的链接打开一次来武装**，没有更省事的办法
（要跨源持久只能挪到 query 或 hash 上，而那正是被 SW 改写掉的东西）。

这条也解释了 11:45 那次「点了半天没记上」和 12:5x 这次「修好了却拿不到读数」其实是**同一个坑的两种表现**。
所以摘除埋点之前，验证一次的成本就是"用新链接重新打开一次"，不是白工。

**推翻的一条（我上一轮的账写错了，这里改）**：
- 0.4.22 的 CHANGELOG 写「布局视口不再被键盘压缩」。**在这台设备上不成立**：
  `innerHeight` 与 `clientHeight` 仍然 **735 ↔ 450**（Δ285 = 键盘高度），
  ⇒ 这台华为浏览器**没有理会 `interactive-widget=resizes-visual`**（不支持或未生效），
  行为仍是「键盘压缩布局视口」。
- 所以「过冲消失」不是换声明的功劳，**真实机制未定**：最可能是 `--kb` 抬起让 composer
  不再参与那串逐帧动画（旧数据里 rz 一步对应一次 composer 高度重排），但没有对照实验，
  我不把它写成结论。**要坐实只能做一次反证**：把 meta 换回 resizes-content 再测一轮，
  看过冲是否回来（需要一次重启）。
- 连带结论：用户要求 ②「页面不动」**只做到了一半**——不弹了，但布局仍在被压缩（scrollTop 随之跳）。
  要做到真·不动，得在 JS 里把 `--app-height` 钉成「无键盘时的 innerHeight」且键盘期间不改它，
  只动 `--kb`；那不再依赖浏览器是否支持 `interactive-widget`。
