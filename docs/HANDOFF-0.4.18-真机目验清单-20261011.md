## 2. 本机量不了、必须真机点的两条

1. **E 的性能账（03:2x 已量，本机这一半结案）**：锚点复原每帧扫 `:scope > .message` 到第一条可见行为止，
   并在 120 ms 内重瞄 3 次。120 行会话（112 行 `.msg-hist`）实测 `T_timing`：
   **半程中位 0.1 ms／上限 0.2 ms；把 120 行全扫完也一样 0.1／0.2 ms；3 次重瞄的最坏合计 0.6 ms**。
   对比一帧 16 ms，余量约 **26 倍** ⇒ 手机要慢过 26× 才可能被看见，量级上不担心，但仍请在真机上
   翻一次几百轮的长会话确认无掉帧。**仍然只有真机能答的那半**：长会话**首屏**耗时（受设备 CPU、
   隧道往返与列表规模影响，本机模拟不出 436 条会话那量级的真实目录）。
   探针：`node F:\defws\tmp\20261011-e-deepclamp.mjs`（同一支里 `T_timing` 段就是这块的数）。
2. **F（键盘收回弹一下）**：**仍未修**，且本轮把两条猜测方向都排除了——
   四支夹具证明「`scrollTop` 被砸到 0 ⇒ 顶边自动取页」在模拟里根本不成立（砸到的是 315/102/385），
   而所有采样在 +80 ms 就稳定，**模拟里没有任何延迟运动**，与用户说的「键盘到家了还在往下延伸」对不上。
   要往下推进只有一次真机观察：在手机上开键盘→打字→收键盘，看**是输入栏跟着落、还是整页内容滞后跟一段**，
   以及有没有可数的「二次移动」。要么由你口述现象，要么我出一个带时间戳埋点的临时构建（需要改 `lib/pages.js`
   + 重启，看完摘掉）——**没有这一条观察，我不改 F 的代码**。
