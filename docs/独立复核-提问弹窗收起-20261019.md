## 三、残余风险（按需处理，不构成阻塞）

1. **M5 存活 = 「关掉提问即复位折叠态」这条契约没有被任何测试钉住。** 代码里确实写了 `if(!pendingQuestion||!pendingQuestion.questions?.length){questionCollapsed=false; …}`，所以现状是对的；但删掉它测试不会红。若将来有人重构这条早退分支，下一个问题会以收起态出现（`.question-actions` 被 `display:none`），用户看到的是一个**没有提交按钮**的卡。当前无实害，属「契约裸奔」。
2. **收起态的底部安全区未被预留。** `.question-composer{padding:10px 0 5px}` **不含** `env(safe-area-inset-bottom)`（对比 `.composer` 是 `calc(5px + env(safe-area-inset-bottom))`）。因此 `host.offsetHeight` 在 iPhone 带home指示条的机型上会比视觉占位少约 34px，收起后最后一行内容可能贴着指示条。此为既有 `.question-composer` 的性质、非本次引入，但**收起态把它变成了常态**（因为收起态就是长期停在那 84~85px 上）。需真机看一眼。
3. **收起态下仍可作答，是设计如此，不是漏洞。** `P-13b` 直接断言「收起后回来点选项能提交」——而收起态里选项按钮是 `display:none` 的，真实用户点不到；页面层也没有任何 `questionCollapsed` 的结算拦截。这是**有意的**（防止「收起 = 卡住问答」的死角），但意味着该用例证明的是「状态机不拦截」，不是「UI 上做得到」。
4. **`--question-h` 从不复位。** 提问结束后变量保留旧值，但消费者要求 `body.question-open.question-collapsed` 双类同时在，空态早退会把两个类都摘掉 ⇒ 陈旧值惰性。读码确认无消费者，不判为缺陷。
5. **收据字节数已被他线 hunk 推过**（见 claim 4）。若后续他线继续加内容，`+54 B` 会继续漂。建议下次动预算时顺手刷新一次注释，别让收据与实测长期背离。
6. **未在真机验证**：本报告全部结论基于读码 + 离线变异 + 字节自算。渲染实测（收起态实际高度、`padding-bottom` 真实生效值、iPhone 安全区观感）**需真机验证**。
